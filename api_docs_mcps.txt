# Apify Trustpilot Reviews Scraper Documentation

## Overview

This benchmark uses the following Apify Actor:

```text
Actor name: Trustpilot Reviews Scraper
Actor developer: automation-lab
Actor ID for Apify Client: automation-lab/trustpilot
Actor ID for REST URL: automation-lab~trustpilot
Current build reviewed: 0.1.44 / latest
Pricing model: Pay per event
```

The Actor extracts Trustpilot reviews, reviewer information, verification data, company replies, ratings, and company metadata.

It supports:

- multiple companies in one run
- company domains
- complete Trustpilot profile URLs
- automatic pagination
- more than 200 reviews per company
- recency or relevance sorting
- rating filters
- language filters
- date filters
- verification filters
- company-reply filters
- JSON, CSV, XML, and Excel output

## Environment Variables

Store the Apify API token and selected Actor ID in `.env`:

```env
APIFY_API_TOKEN=your_actual_apify_token
APIFY_ACTOR_ID=automation-lab/trustpilot
```

Rules:

- Never hardcode the API token.
- Never print the token.
- Never save the token in raw request files.
- Never include the token in reports.
- Never commit `.env` to Git.
- Use the `Authorization` header rather than a URL token parameter.

---

## Authentication

Apify uses Bearer-token authentication:

```http
Authorization: Bearer YOUR_APIFY_API_TOKEN
```

Example:

```bash
curl \
  --request POST \
  --url "https://api.apify.com/v2/acts/automation-lab~trustpilot/runs" \
  --header "Authorization: Bearer $APIFY_API_TOKEN" \
  --header "Content-Type: application/json"
```

Start an asynchronous Actor run:

```http
POST https://api.apify.com/v2/acts/automation-lab~trustpilot/runs
```

The endpoint immediately returns an Actor Run object.

Important response fields include:

- `id`
- `actId`
- `status`

- `finishedAt`
- `defaultDatasetId`
- `defaultKeyValueStoreId`
- `defaultRequestQueueId`
- `stats`
- `usage`
- `usageUsd`
- `usageTotalUsd`

The benchmark must save the Run ID immediately after creation.

## Benchmark Actor Input

Use one Actor run for all five approved companies:

```json
{
  "companyUrls": [
    "www.thepearlsource.com",
    "www.shein.com",
    "temu.com",
    "www.aliexpress.com",
    "thehalara.com"
  ],
  "maxReviewsPerCompany": 200,
  "sort": "recency",
  "includeCompanyInfo": true
}
```

Target:

```text
5 companies × 200 reviews = 1,000 reviews
```

The script must use `benchmark-domains.json` as the source of truth.

It must not automatically add, replace, or remove domains.

## Input Parameters

### `companyUrls`

```text
Type: array of strings
Required: yes
```

Accepts:

- company domains
- full Trustpilot company-profile URLs

Examples:

```json
{
  "companyUrls": [
    "pipedrive.com",
    "https://www.trustpilot.com/review/pipedrive.com"
  ]
}
```

Multiple companies may be supplied in a single Actor run.

---

### `maxReviewsPerCompany`

```text
Type: integer
Default: 0
```

Defines the maximum reviews collected for each company.

Examples:

```text
20 = maximum 20 reviews per company
200 = maximum 200 reviews per company
0 = no configured review limit
```

For the standard benchmark, use:

```json
{
  "maxReviewsPerCompany": 200
}
```

The Actor documentation states that pagination is automatic and that setting this value to `0` allows all available reviews to be collected.

Therefore, this Actor does not advertise a fixed 200-review-per-business limitation.

---

### `sort`

```text
Type: string
Default: recency
```

Supported documented values:

```text
recency
relevance
```

For the benchmark, use:

```json
{
  "sort": "recency"
}
```

---

### `stars`

```text
Type: array
Default: all ratings
```

Supported values:

```text
1
2
3
4
5
```

The benchmark should leave this empty so all ratings are included.

---

### `languages`

```text
Type: array
Default: company/default language
```

Example:

```json
{
  "languages": ["en", "fr", "de"]
}
```

The standard benchmark should not apply a language restriction unless required by the live Actor input schema.

---

### `date`

```text
Type: string
Default: all time
```

Documented values:

```text
last30days
last3months
last6months
last12months
```

The benchmark should leave this unset so it can retrieve the latest 200 reviews without applying a date-range restriction.

---

### `verified`

```text
Type: boolean
Default: false
```

When enabled, only verified reviews are returned.

For the benchmark, keep it disabled so verified and unverified reviews are both included.

---

### `withReplies`

```text
Type: boolean
Default: false
```

When enabled, only reviews with company replies are returned.

For the benchmark, keep it disabled.

---

### `includeCompanyInfo`

```text
Type: boolean
Default: true
```

When enabled, company metadata is added to review records.

For the benchmark, use:

```json
{
  "includeCompanyInfo": true
}
```

## Asynchronous Run Workflow

The benchmark should use this workflow:

1. Validate `.env`.
2. Validate the Actor ID.
3. Save the sanitized Actor input.
4. Start one Actor run.
5. Save the returned Run ID.
6. Poll the same Run ID.
7. Wait for a terminal status.
8. Save the final Run object.
9. Obtain `defaultDatasetId`.
10. Retrieve all dataset items.
11. Save raw dataset responses.
12. Normalize and deduplicate reviews.
13. Generate final reports.

The script must never poll by creating another Actor run.

---

## Run Status Endpoint

Retrieve the existing Actor run:

```http
GET https://api.apify.com/v2/actor-runs/{runId}
```

Example:

```bash
curl \
  --request GET \
  --url "https://api.apify.com/v2/actor-runs/RUN_ID" \
  --header "Authorization: Bearer $APIFY_API_TOKEN"
```

Possible terminal statuses include:

```text
SUCCEEDED
FAILED
ABORTED
TIMED-OUT
```

Possible non-terminal statuses include:

```text
READY
RUNNING
```

The live API response is the source of truth for exact status values.

---

## Polling Rules

The benchmark must:

- poll the same Run ID
- wait between polling requests
- save every status check
- stop on a successful terminal status
- record failed, aborted, or timed-out runs
- not start another run automatically
- not silently accept incomplete results

After completion, wait briefly and retrieve the final Run object again so finalized usage and cost information can be captured.

## Dataset Retrieval

Actor results are stored in the Run’s default dataset.

Use the `defaultDatasetId` returned by the Run:

```http
GET https://api.apify.com/v2/datasets/{datasetId}/items
```

Recommended request:

```http
GET /v2/datasets/{datasetId}/items?format=json&clean=true&offset=0&limit=1000
```

Example:

```bash
curl \
  --request GET \
  --url "https://api.apify.com/v2/datasets/DATASET_ID/items?format=json&clean=true&offset=0&limit=1000" \
  --header "Authorization: Bearer $APIFY_API_TOKEN"
```

- `offset`

- `clean`
- `fields`
- `desc`

- `X-Apify-Pagination-Offset`
- `X-Apify-Pagination-Limit`
- `X-Apify-Pagination-Count`
- `X-Apify-Pagination-Total`

The benchmark should:

1. Request dataset items.
2. Save the raw response.
3. Read the pagination headers.
4. Compare returned count with the total.
5. Continue with a larger offset when required.
6. Detect repeated offsets or repeated items.
7. Stop when all items have been downloaded.

Dataset retrieval must not create another paid Actor run.

## Successful Review Definition

A successful review must contain:

- `reviewId` or `reviewUrl`
- `rating`
- `publishedDate`
- `title` or `text`
- `authorName` or `authorId`
- `companyDomain`
- non-empty review data
- no error object
- no duplicate

Only valid unique reviews count toward the 1,000-review target.

---

## Duplicate Detection

Use this priority:

1. `reviewId`
2. `reviewUrl`
3. stable Actor-provided source ID, if verified
4. deterministic SHA-256 hash using:

```text
companyDomain
authorName
publishedDate
rating
title
text
```

Detect:

- duplicates within one company
- duplicates across companies
- duplicates across dataset pages
- duplicates caused by retries
- duplicates caused by repeated Actor runs

Duplicates must not count toward the final successful-review total.

---

## Multi-Company Behaviour

The Actor supports multiple company domains in one run.

Each result contains company fields such as:

- `companyDomain`
- `companyName`
- `companyUrl`

The benchmark must group records by the normalized company domain and verify:

```text
www.thepearlsource.com — target 200
www.shein.com — target 200
temu.com — target 200
www.aliexpress.com — target 200
thehalara.com — target 200
```

Domain normalization may need to handle cases where Trustpilot uses a domain without the `www` prefix.

Do not treat a harmless `www` normalization difference as another business.

## Retry Policy

Retry only:

- temporary network failures
- HTTP 429
- HTTP 500–599
- temporary Run-status retrieval failures
- temporary dataset-download failures

Do not automatically retry:

- HTTP 400
- HTTP 401
- HTTP 402
- HTTP 403
- invalid Actor ID
- invalid Actor input
- a completed paid Actor run

This normalized calculation shows cost efficiency, but it does not mean the 1,000-record benchmark was completed.

# Outscraper Trustpilot Reviews API Documentation

## Overview

The Outscraper Trustpilot Reviews API retrieves reviews from businesses listed on Trustpilot.

It accepts either:

- a business domain
- a complete Trustpilot business profile URL

Examples:

```text
www.thepearlsource.com
https://www.trustpilot.com/review/www.thepearlsource.com
```

---

## Official Sources

```text
Trustpilot Reviews API documentation:
https://docs.outscraper.com/endpoints/trustpilot-reviews/

Request Results documentation:
https://docs.outscraper.com/endpoints/requests-requestid/

Trustpilot Reviews product page:
https://outscraper.com/trustpilot-reviews-api/
```

---

## Authentication

Outscraper uses an API key sent through the request header:

```http
X-API-KEY: YOUR_API_KEY
```

The API key must be stored in `.env`:

```env
OUTSCRAPER_API_KEY=your_actual_api_key
```

The API key must never be:

- hardcoded in scripts
- printed in logs
- included in screenshots
- saved in reports
- committed to GitHub

---

## Main Endpoint

```http
GET https://api.outscraper.com/trustpilot-reviews
```

Official code examples may also use:

```text
https://api.outscraper.cloud/trustpilot-reviews
```

The benchmark should use one host consistently for task creation and must use the exact `results_location` URL returned by Outscraper for async result polling.

---

## Request Parameters

### `query`

- Type: array of strings
- Required: yes

The query can be a domain or Trustpilot profile URL.

Example:

```text
query=www.thepearlsource.com
```

Multiple queries can be included in one request.

The documentation supports batching up to 1,000 queries.

Example:

```text
query=www.thepearlsource.com
query=www.shein.com
query=temu.com
```

---

### `limit`

- Type: integer
- Required: no
- Default: 100

Defines the maximum number of reviews requested for each query.

Example:

```text
limit=200
```

The actual number returned must be verified from the response.

A requested limit must not automatically be treated as a successful record count.

---

### `skip`

- Type: integer
- Required: no
- Default: 0

Used for review pagination.

The value must be a multiple of 20.

Valid examples:

```text
skip=0
skip=20
skip=200
skip=400
skip=600
skip=800
```

Invalid example:

```text
skip=25
```

---

### `languages`

- Type: string
- Required: no
- Default: `default`

Supported documented values include:

```text
default
all
en
es
de
```

For the benchmark, use:

```text
languages=all
```

This prevents reviews from being excluded only because of their language.

---

### `sort`

- Type: string
- Required: no

Supported value:

```text
recency
```

For the benchmark, use:

```text
sort=recency
```

This requests the newest reviews first.

---

### `cutoff`

- Type: integer timestamp
- Required: no

Defines the oldest timestamp that may be returned.

Using `cutoff` overrides the `sort` parameter and returns the newest matching records first.

The benchmark should not use `cutoff` unless date-based filtering is intentionally being tested.

---

### `fields`

- Type: string
- Required: no

Defines which response fields should be returned.

By default, Outscraper returns all available fields.

Example:

```text
fields=query,review_id,review_rating,review_title,review_text
```

The benchmark should initially request all fields to measure complete field coverage.

---

### `async`

- Type: boolean
- Required: yes
- Default: true

Supported values:

```text
async=true
async=false
```

`async=true` submits the scraping request and returns a request ID.

`async=false` keeps the HTTP connection open until the task finishes and may be more vulnerable to timeout.

The benchmark should use:

```text
async=true
```

---

### `ui`

- Type: boolean
- Required: no
- Default: false

When enabled, the request is executed as a platform UI task.

Using `ui=true` forces asynchronous execution.

The benchmark does not require UI mode.

---

## Example Benchmark Request

```bash
curl --request GET \
  "https://api.outscraper.com/trustpilot-reviews?query=www.thepearlsource.com&limit=200&skip=0&languages=all&sort=recency&async=true" \
  --header "X-API-KEY: $OUTSCRAPER_API_KEY"
```

---

## Asynchronous Workflow

### Step 1 — Create the task

Send a request to:

```http
GET /trustpilot-reviews
```

A successful async submission normally returns:

```json
{
  "id": "request-id",
  "status": "Pending",
  "results_location": "https://api.outscraper.cloud/requests/request-id"
}
```

The task creation response must be saved immediately.

---

### Step 2 — Save request information

Save:

- request ID
- results location
- query
- limit
- skip
- task creation timestamp
- HTTP status
- sanitized request parameters

---

### Step 3 — Poll the returned results URL

Poll the exact `results_location` returned by the task creation response.

Do not create another `/trustpilot-reviews` task while waiting.

Example:

```http
GET https://api.outscraper.cloud/requests/REQUEST_ID
```

---

### Step 4 — Handle task status

Possible statuses include:

```text
Pending
Success
Failure
```

#### Pending

The task is still running.

Wait before checking the same result URL again.

#### Success

The result is ready and should be saved immediately.

#### Failure

Record the failure, error details, timing and request ID.

Do not silently discard it.

## Request Results Endpoint

```http

```

Optional parameter:

```text

```

When `flat=true` is used, results from multiple queries may be combined into one array.

The benchmark should preserve domain information even when using a flat result.

## Result Expiration

Completed async responses remain available for approximately four hours.

The benchmark must therefore:

1. poll the task until completion
2. save the full raw response immediately
3. not depend on retrieving it again after expiration

An expired response may no longer return the completed result.

For a 1,000-review single-domain test, use separate pages:

```text
Page 3: limit=200, skip=400
Page 4: limit=200, skip=600
Page 5: limit=200, skip=800
```

Each page must be treated as a separate scraping request.

The benchmark must verify that:

- each page contains different review IDs
- older reviews appear as `skip` increases
- the same page is not returned repeatedly
- duplicate reviews are not counted twice
- empty pages are logged
- pagination loops are detected
- total successful unique records are calculated after deduplication

A request with:

```text

```

must not be assumed to return 1,000 reviews without verification.
